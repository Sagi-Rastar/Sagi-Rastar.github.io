一块黑屏的 TFT：从 RTT 日志到 QSPI 虚焊

硬件 #PSoC6 #QSPI #XIP #硬件调试 #FCT #AI辅助

VESPA UI EB3 build FCT 不良复盘

EB3 build FCT 不良复盘 · NG_1 64200103255814624264300150 平台：VESPA UI（PSoC6 CY8C6144 + LVGL 8.4 + 外挂 XM25QH64D 8MB QSPI Flash，LVGL/页面代码跑在 XIP）

0. 引子：最花时间的，是"曾经好过"的不良

EB3 build 的 FCT 报表里，这台模组的表现很典型：

  • 上电黑屏，夹具发 (TEST) 串口没有任何应答；
  • 但它在 FCT1、FCT2 都是 PASS，FCT2 还读到了 TFT / Touch 的版本号；
  • 工站报的 Failed Msg 是 1.1.2 All LED ON Check_Block_1_2(3) —— 可实际上连屏都没亮，根本轮不到 LED 检查。

"曾经好过、现在不亮、时好时坏"——整个过程我觉得挺值得写一篇笔记进行记录，并且有四点主要的复盘点：

  1. 先写交叉验证矩阵再动手；
  2. 硬件先行，先测供电和基本功能；
  3. 用 J-Link 读 RTT 日志 + AI 辅助，把"日志断在哪"翻译成"代码走到哪"；
  4. 不急着补焊，保留现场，多次读数找规律，最后从数据里算出坏的是哪一根引脚。

1. 先认识这个模组：硬件与软件背景

1.1 模组由什么组成

VESPA UI 模组 = TFT PCBA（D）+ Touch PCBA（C）+ LCD 屏 + 旋钮/按键/LED 显示，装在咖啡机面板上。

板 关键器件 作用
TFT PCBA（D） CY8C6144LQI-S4F82（PSoC6，QFN-68） 主控：跑 LVGL UI、TFT 驱动、USCP/BRSCOM/MCP 协议
XM25QH64D（64Mb QSPI NOR，SOIC-8） 存 UI 代码 + 图片/字模（XIP 执行）+ OTA 镜像
LCD 12pin FPC 连接器（J3） TFT-RST / SDA / SCL / CS / RS + TE + 背光
24MHz 晶振、旋钮编码器（EN1/EN2/SW1）、SWD 调试口（J5） 时基、旋钮输入、调试
背光驱动（MOSFET + 限流电阻，PWM 调光） 屏背光
Touch PCBA（C） CY8C4025LQI-S411（PSoC4，QFN-24） 触摸/按键采集、LED 显示、与 TFT 通信
Aip33A07（LED 显示驱动）、RGB LED、4 个按键 面板 LED 显示与按键
JW5101（24V→5V）、AiP6026E（5V→3.3V） 电源树
J1（接主板）、J2（12pin，接 TFT） 对外/对内连接器

1.2 通信拓扑

链路 物理连接 协议 用途
夹具/上位机 ↔ TFT AUX UART：J1 → Touch 板（门控/透传）→ J2 → TFT（SCB4） USCP（ASCII 命令，如 (TEST)） FCT 测试、版本读取、产线 OTA
主板 ↔ TFT BRSCOM UART（SCB2） BRSCOM 帧协议 咖啡机主控与 UI 的命令/状态
Touch ↔ TFT MCP UART（SCB1） rts_mcp 帧 触摸/按键事件、启动握手、OTA 协同
TFT ↔ LCD SPI（SCB0） NV3002B 命令 显示
TFT ↔ Flash QSPI（SMIF，1-4-4） — UI 代码/图片 XIP + 镜像存储

1.3 软件与存储架构

两个工程：

  • VespaTFTBoot（Bootloader，内部 Flash 前 32KB）： 上电先看复位原因；POR/XRES 时若检测到 AUX_RX 被拉高（Serkit/夹具在位）就进入 OTA，通过 AUX UART 收 S19，先整片擦除外部 QSPI，再分别写内部 Flash 和外部 Flash；否则软复位跳到 App。
  • VespaTFTApp（应用，本 build 是 FCT 固件）： 单核 CM4、无 RTOS，用协作式调度器（RTS，protothread）在主循环里轮询 9 个线程；UI 用 LVGL 8.4；FCT 固件只跑 FCT 页面 + USCP 测试协议 + BRSCOM 桩。

存储布局：

区域 大小 内容
内部 Flash 256KB Bootloader 32KB + App；末尾 16KB 是 NVM（4 bank × 4KB，带 CRC32）
外部 QSPI 8MB LVGL 代码（lv_*.o）、页面代码（ui_page*.o、screens.o）、大图片/字模（.cy_xip_code）

这是理解本次不良的关键：屏幕 UI 的代码和图片全部在外部 Flash 上，CPU 是直接从外部 Flash 取指执行（XIP） 的。所以外部 Flash 一旦读不到，MCU 内部 Flash 的启动代码还能跑（能打日志）

开机后第一次执行外部 Flash 里的代码，是 app_main() 里的 detect_fct_mode()（读 J4 PIN8 的短接状态，决定进 FCT 页面还是等待页）。本次不良的日志正好断在它前面。

5. 把代码和日志丢给 AI：从"日志断在哪"到"代码走到哪"

这是这次排查的转折点。

硬件工程师对代码执行顺序不一定熟，但日志断点 + 源码是 AI 最擅长的翻译工作。我把三样东西给了 AI：

  1. 好板 / 坏板的 RTT 日志；
  2. 代码仓库路径（VespaUITFT，含 Bootloader 和 App 两个工程）；
  3. 现象描述（黑屏、串口无应答、FCT1/FCT2 曾 PASS）。

AI 给出的分析非常关键：

  • 按 app_main() 的执行顺序，nvm: boot bank 3 对应 nvm_boot_init() 的最后一行；
  • 从这一行到下一条日志 page init... 之间，会执行的函数调用链有：uart_uscp_init() → USCP_handler_init() → detect_fct_mode() → __enable_irq() → 第一轮主循环 → thread_lvgl → ui_user_init() → driver_tft_init()；
  • 其中前两个是纯外设配置、没有等待；detect_fct_mode() 是第一次执行"外部 Flash 里的代码"（ui_page_fct.o 被链接到 XIP 区 0x18000000）；
  • 所以最可疑的假设是：外部 QSPI 读不到，CPU 取指到 0xFFFFFFFF，触发 HardFault。

这一步为什么重要：它把"日志停在这里"这种模糊现象，变成了一个可以用 J-Link 一条命令验证的假设。 AI 不替你做判断，但它能把"硬件工程师不熟的代码执行链"翻译成"可验证的下一步"。

6. J-Link Commander：一条命令验证假设

用 J-Link Commander 读关键地址（不是 RTT Viewer，它没有命令控制台）：

翻译一下：

  • 0x10008000 是 App 向量表（初始 SP + Reset_Handler），内部 Flash 是好的；
  • 0x18000000 全 FF → 外部 QSPI 读不到；
  • CFSR=0x00010000 → CPU 执行了未定义指令，也就是 0xFFFFFFFF；
  • RES_CAUSE=0x11 → 板子在 WDT 复位和软复位之间循环（fault → 4.1 s 被狗复位 → 再来一遍）。

假设完全成立：App 从内部 Flash 启动 → 第一次调用外部 Flash 里的函数 → 取指 0xFFFFFFFF → HardFault → 看门狗复位 → 死循环 → 永远黑屏。

7. 别急着补焊：先保留现场，做"按压实验"

补焊会把现场破坏掉，而且如果根因不是焊接，补完还是不良，反而更难查。

先做两个实验：

  1. 按压实验：用手稍用力按住 Flash 芯片，重新上电 → 正常显示 FCT MODE；
  2. 重复读数：按住时读两次、不按住时读两次，看数据是否可重复。

结果：

状态 0x18000000（4 字） 0x1802277C（4 字）
按住（第 1 次） CFCCFF00 DB6CC03C 9BED6FFB 1EFC3100 180226C1 18022605 18022621 00004770
不按住（第 1 次） CFCCFF00 DF6CC47C DFED6FFF 5EFC7544 5C4666C5 FCC67704 644F4744 F4444C7C
按住（第 2 次） CFCCFF00 DB6CC03C 9BED6FFB 1EFC3100 180226C1 18022605 18022621 00004770
不按住（第 2 次） CFCCFF00 DF6CC47C DFED6FFF 5EFC7544 FFFFFFFF FFFFFFFF FFFFFFFF FFFFFFFF

两次"按住"读数完全一致，两次"不按住"也高度一致 → 机械按压可稳定复现，是接触/焊接问题，不是 Flash 内容问题。

而且"按住"时 0x1802277C 读出的 180226C1 / 18022605 / 18022621 是三个奇数地址（Thumb 函数指针），00004770 是 bx lr —— 正是页面结构体 rts_gui_page_t page = {.init, .loop, .uninit}，和好板日志里的 page init...(0x1802277c) 完全对得上。Flash 里的内容本来就是好的。

8. 扩展：从数据里找规律，坏的是哪一根线？

不按住时不是每次都全 FF，而是部分位翻转。把"按住"和"不按住"的 0x18000000 做异或：

每个字节里只有 bit2 和 bit6 在翻转。

QSPI 是 4 线并行，一个字节两个时钟：

所以：bit6 和 bit2 都归 IO2 管 → 坏的是 IO2 这条数据线。

再往下看一层：所有异常字节的 bit2/bit6 全是 1（7C/C4/6C/DF、FF/ED/6F/DF、44/75/FC/5E 全部满足），而正常数据里这些位是有 0 有 1 的 → IO2 被恒定读成 1，这是"线开路/浮空被拉高"的典型特征。

最后落到器件手册：这颗 Flash 是 XM25QH64D（64Mb，SOIC-8；SMIF 配置沿用 W25Q64CV 兼容参数）：

pin 名称 四线模式
1 /CS /CS
2 DO IO1
3 /WP IO2 ← 重点
4 GND GND
5 DI IO0
6 CLK CLK
7 /HOLD IO3
8 VCC VCC

pin 3（/WP，四线模式下就是 IO2）虚焊。

从"黑屏"到"pin 3"，中间全部是可验证的数据，没有靠猜。 异或、位映射、手册查询这些"算"的部分，也可以让 AI 一起做，人负责验证。

9. 根因与措施

根因：外部 QSPI Flash 焊接不良（pin 3 ，或整体爬锡不良/虚焊），XIP 读数据时 IO2 恒为 1，CPU 取指到非法指令 → HardFault → 看门狗复位环 → 黑屏。

11. 一句话总结

黑屏不等于软件死机。先问两个问题：CPU 停在哪？它在读什么？ 这次答案分别是：HardFault 里，和一颗虚焊的 Flash。
